# ManiMind 上下文与状态设计

## 一、为什么要分层

这个项目天然会产生两类信息：

- 一类是必须长期保留、跨镜头复用、影响后续所有决策的事实
- 一类是只在单次协作或单个镜头内有意义的临时信息

如果两者混在一起，后果会很直接：

- 主 Agent 会被临时草案污染
- 审核 Agent 无法区分“已批准结论”和“临时猜测”
- 重试时很难判断哪些内容应该保留

## 二、长期上下文

路径：

```text
runtime/projects/<project_id>/
```

推荐文件：

- `project_manifest.json`
- `research_summary.md`
- `glossary.json`
- `formula_catalog.json`
- `style_guide.json`
- `storyboard.json`
- `review_report.json`
- `state.json`

写入原则：

- 只写稳定结论
- 每次写入要有来源和时间戳
- 可以被审核 Agent 直接消费

## 三、短期上下文

路径：

```text
runtime/sessions/<session_id>/
```

推荐文件：

- `handoff.json`
- `segment-<id>-notes.md`
- `worker-<name>-result.json`
- `retry-log.json`
- `blocking-issues.json`

写入原则：

- 只面向当前轮协作
- 允许频繁覆盖和重试
- 不作为最终事实来源

## 四、状态对象

项目状态至少包含以下字段：

- `project_id`
- `stage`
- `input_assets`
- `approved_storyboard_version`
- `active_session_id`
- `worker_statuses`
- `review_status`
- `next_action`

## 五、状态迁移规则

1. 主 Agent 推进阶段时更新项目级 `state.json`
2. 子 Agent 只更新自己的短期协作状态，不直接改项目总状态
3. 二级协调 Agent 汇总子 Agent 结果后，才能推动 `DISPATCH -> REVIEW`
4. 审核 Agent 是唯一能推动 `REVIEW -> POST_PRODUCE` 的角色

## 六、推荐序列化格式

- 面向机器消费的状态与任务表用 `json`
- 面向人类阅读的研究总结与脚本用 `md`
- 大体量产物索引使用 `json` 清单指向真实文件
